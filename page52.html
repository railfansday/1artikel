A Critique of GPUI

📅 2026-11-09  |  Read Source →

Recently, there has been a trend of more desktop GUI apps being built using native rust GUI frameworks. And there are now even well known electron apps getting official rewrites: Discord announced their app is being rewritten using GPUI.1 Meanwhile, a lot of the LLM-clones being published seem to choose egui. In this post, I want to explain why I am not sure those frameworks are a good foundation to build on.

To put it plainly: I believe both GPUI’s and egui’s state models are dead ends for complex desktop applications. Both are impressive projects, and they have their place. Zed genuinely feels fast and nice to use, and I use egui myself for debug interfaces in bevy games. But I don’t think those frameworks should be the default choice for native desktop apps.

Disclosure: I ported GPUI’s current Linux renderer to wgpu2, I built the benchmark harness used below, and I work on zgui, a signal-based Rust framework that appears in the charts.

Raph Levien quotes Ron Minsky: “hidden inside of every UI framework is some kind of incrementalization framework.”3 A UI is a function of state, and state changes a little at a time. But if that function becomes expensive, you might want to start looking for ways to derive a faster way to update pixels on the screen from an incremental state change. So every framework has to answer one question: when one value changes, what runs?

I understand why people like the first three. No state to synchronize, one place where state lives, a render function that is plain Rust, no macros or separate compiler. I’m gonna make the argument that these approaches don’t scale, and fixing the underlying problem defeats what makes these models simple and easy to reason about.

GPUI calls itself “a hybrid immediate and retained mode” framework.4 It retains state in entities. The UI is defined in render functions, changing state must trigger a rerun.

It is ordinary Rust. You can use if, for and local variables, and there aren’t any weird wrappers. State changes require an explicit notification:

notify carries the entity id.5 Since Rust doesn’t have a write barrier on &mut, GPUI cannot see which field changed (or whether anything changed at all). The Angular team wrote this about zone.js in 2023: it “is only capable of notifying us when something might have happened”, and “This approach has not scaled well.”6 notify is more precise than a zone, since it names an entity, but ultimately it makes the same kind of statement. Below that id, GPUI knows nothing, so it re-renders every view that is not behind a valid .cached() boundary. And in practice, GPUI often rerender every view, because .cached() is rarely used by application authors, and imposes certain restrictions on layout semantics.

GPUI has a reputation of being “fast”. And while constants might be relatively low, asymptotically, it is leaving a lot on the table. So I ran a few benchmarks, that specifically test how much a sparse state change in a large UI actually costs.

At 3,000 live rows with a cached view per row, changing one label takes 8.4 ms. A hover, a keystroke and writing a value equal to the old one all cost about the same, because the cost follows the tree and not the change. It grows by about 3 ms per 1,000 live rows. Write the rows as plain elements, as in the code above, and the same label takes 92 ms. A hand-written equality guard takes the equal write from 7.9 ms to 0.9 µs (demonstrating how much is left for each call site to find).

This doesn’t mean that every GPUI app is slow, but it shows the limit of the state model. Especially with more expensive layout, you do hit this wall in practice. Zed might feel fast, but the truth is that Zed is a relatively simple app, UI wise. The app’s chrome contains a few buttons, in a simple layout, a sidebar and a text editor, and the text editor is implemented as a custom element, completely bypassing GPUI’s layout and view semantics. By their own account, a window “has tens of nodes and a few thousand elements”.7

The obvious fix is to retain more. Zed has experimental branches for this, and Longbridge’s gpui-fast is a fork that keeps every view’s subtree between frames.8 9 It works, within a limit: the smallest thing either one can reuse is a view. RenderOnce components, which is what buttons and rows are, draw inside their parent’s view and are no boundary at all. List rows are closures, so a row view means managing a keyed map of entities by hand.

And it only helps where state happens to line up with views. I reran gpui-fast’s own 60-panel benchmark, drew each frame once, and then moved the state:

With state owned by each panel, one change saves 83%. With a shared model, retention makes the same frame 11% slower. The window and the edit are identical. In real Zed, the Zed team measured retention “1–3% slower than off on ordinary workloads”, found that “Most of the real-Zed win” came from other work, and warned that “microbenchmark wins didn’t predict real-Zed results”.8 gpui-fast is real progress and costs little to adopt: it takes the 3,000-row label from 8.4 to 3.4 ms. But that frame renders three views and lays out one element, and still spends 3.4 ms, because the frame is still a walk over the whole tree.

This is the part I find hardest to get past. People choose GPUI because render is a plain function of state. A UI where each projection is a separately owned entity with a subscription and a guard is no longer that. It is a signal graph built by hand from much heavier parts, where a missed edge is silent. Zed’s own design note says “Missing notifications are application bugs”.12 Keep the pleasant API and you get view-sized updates. Take the precision and you lose the pleasant API. A signals crate on top would not change the trade, because its smallest sink is still a view. Reaching one node with no render running needs writes the framework can see and nodes that outlive a frame, and that means a new state model and a new element contract.

At the size it is usually shown, the Elm architecture is a deceptively simple UI model: one state value, one update, one view, and every change has a name. While large applications do use it successully,13 14 I do want to make the point that this clarity belongs to the small case, and in a complex application signals and stores are arguably easier to reason about.

Take the same unread count. It has to be right after every message, so either view recomputes it on every update or update maintains it:

The definition of unread is now nowhere in particular. It is spread across every arm that touches a thread, and each new message has to remember it. The compiler checks that the match is exhaustive, but it does not check the arithmetic. The memo above has one definition, and a new writer cannot forget it.

The same thing happens with location. Where does a hover state or a half-typed draft live? Single source of truth says in the model, with a message type routed down and an outcome routed back up. Elm’s guide: “Actively trying to make components is a recipe for disaster in Elm.”15. Iced recommends returning an Action to the parent.16 Iced’s maintainer says components in this architecture always end “with pain”, and also makes the best case for the discipline: avoiding them “forces you to think hard about your data model”.17 Okay, I guess that’s a fair argument. But cosmic-files has 136 top-level message variants and 73 more for a tab, plus a Tab::update that returns commands for the parent to interpret.18 Everything in that is explicit, and none of it is simple.

The architecture also has the same issue GPUI has. The update implementation tells you what a message writes, it cannot tell you what read the field. Anything inside the view might. Elm’s architecture doesn’t answer “what changed?”, it answers “what happened?”. Session export might be useful in some scenarios, but it is not useful for scalable performance characteristics.19

This is what I read in the web’s history. Redux is the best-known relative of this design, and its docs read like a field report. Treat a portion of your store “as if it were a database”.20 Selectors “will be re-run after every dispatched action”.21 The core package is “obsolete”, replaced by a toolkit made to remove boilerplate.22 Outside React, the mainstream has moved to tracked reads. Angular, Vue, Svelte and Solid build on signals or something equivalent, Preact offers them, and Svelte’s team put it this way: “we’ve come to the realisation that Knockout was right all along.”23 Inside React, Jotai and MobX bring tracking in as libraries, and Legend-State even offers a “render once” style.24 Most applications are still on React, and React’s team disagrees, which I come back to below. So the convergence is on the state model, outside one large exception.

Performance follows the same line. Since Iced rebuilds all of view after every batch of messages, one label at 3,000 rows builds 39,023 widgets and takes 7.3 ms. Lazy on every row only gets that to 5.7 ms, because view still has to visit each row to hash its key. The official lazy example keys on a version: u8 that four update arms bump by hand.25 That is a dirty flag with a nicer name. In fairness, cosmic-files and Halloy use no lazy at all, and on a virtualized list Iced is one of the fastest frameworks I measured, at 0.19 ms. A bounded screen rebuilds cheaply. But asymptotic complexity is clear. And similar to GPUI, the API semantics simply can’t express the necessary information.

There is actually precedence for this: Vizia shows what happens when you add precision to this model. It moved from lenses to signals in March 2026 and kept its Model and event dispatch.26 This is its counter, shortened:27

The label reads the signal directly, and the same closure that builds the button created it. The enum, the dispatch and the handler exist to carry one call to update. Vizia was never strict Elm, since its views are built once, and signals were a sensible move: it got per-field writes. But look at what remains of Elm’s reasons. State is a graph of mutable cells, Model is a bag of handles, and event is a &mut self side effect. You now have two systems for saying that something changed. So my objection to adding signals to the Elm architecture really is the same as with GPUI: they work, and they remove what you came for.

egui’s pitch is the best in the field: “You don’t have to worry about app state and GUI state being out-of-sync”.28 For a tool, this is hard to beat:

The price is that a frame costs the size of the UI, independent of what changed. At 3,000 rows every small edit takes about 32 ms, or about 19 ms with accessibility off. egui’s author is candid about the trade: immediate mode is “easier to use, but less powerful”.28

As the application grows, the original attraction goes. The layout paradox is “a fundamental shortcoming”.28 Long lists need show_rows, which takes one fixed row height. Rerun, the largest egui application I know of, clamps queries by “inspecting egui state from the previous frame”.29 Anything expensive goes behind a cache keyed on your data. A cache that has to agree with your data is the synchronization problem immediate mode set out to remove, now in application code, one frame late.

Two things stand out. Iced’s factor is small because the view function still runs. And Floem’s coarse case is worth a look: every cell reads one global revision signal, which is notify in signal clothing. It is the slowest result on the chart. So signals do not rescue coarse state. The React team found the same thing from the other side: on a benchmark with “one giant input”, a signals-style runtime disappointed, and Joe Savona concluded the data model “is just as important, maybe more so” than the algorithm.30 The state has to be shaped like the reads. That is why I call this a state model problem. A good API should make it easy to align the data model with its UI projection.

Suppose you accept all of that. You want the framework to track reads, and you want state shaped to match. What is the simplest API?

That is the whole thing. The body runs once. The closures you hand to the framework run again when something they read changes. A local variable is a local variable. There are no hook rules, no dependency arrays, no stale closures and no PartialEq on props. Nothing reconstructs a row’s identity, because the row is still there.

Compare signals with re-running components, which is Freya’s model. It works well: one keystroke at 3,000 rows costs 1.2 ms. But look at a counter:31

use_state exists because that line runs again. You now hold both models: read tracking decides which scope re-runs, and then re-render semantics apply inside it, with hooks, prop equality and a diff. Finer updates need smaller components, which is GPUI’s problem at a much lower price. What the re-running body buys is ordinary control flow, and that is the serious objection.

Dan Abramov makes a compelling argument.32 Run-once puts your rendering logic in closures, so top-level control flow stops working, and you group code around values and not around logic. “The beauty of React is that making things ‘computed’ is an optimization, not a requirement.” He is right about it. This compiles, but the first line never updates:

A reactive if has to become a dyn_container, and a for a dyn_stack. Solid 2.0 had to add dev warnings for top-level reads.33

But the same comment contains the reason I land the other way. He says Solid’s regrouping is “Similar to how you have to restructure your code around the values when you optimize it with useMemo.” Exactly. If your application never needs that, React’s model may be simpler. If it does, you pay for the regrouping either way, and the only choice is when: from the start, or later under a profiler. Ryan Carniato’s reply is the one I agree with: “In Solid you always write as if the data is derived so you don’t refactor to optimize.”32 Once you know you want this precision, run-once is the API that stops pretending otherwise. The failure modes also favour it. A forgotten hole goes stale on the first update, in the place you wrote it. A forgotten notify depends on what else happened to redraw.

To be perfectly honest, the ecosystem’s wider convergence is on read tracking in general, and not on run-once specifically. Angular considered per-binding updates and chose per-view, in writing, and it lands within about 1 ms of Solid on a partial update.6 34 Apple and Google, who control their languages, kept re-running bodies with @Observable and Compose.35 36 A hole is itself a re-run scope, so what differs is how big the default scope is. Two things I want to note on this though:

View-level rerun and fine-grained signals can have the same performance ceiling. But signals encourage fine-grained state projections and memoization from the beginning, for view-level rerun its an explicit choice that often leads to more boilerplate.

Fine-grained reactivity does not make an app fast on its own.

Floem’s reactivity does exactly what it promises. Changing a label runs 5 effects and spends 0.01 ms in reactive work, then about 14 ms in layout, because Taffy does not know that one leaf moved. (Floem also has a known bug where that edit never repaints, so treat this as a floor.) Vizia runs 4 bindings, then walks all 120,091 entities, for 46 ms. Slint writes an equal value in 4 µs, and takes 172 ms for a label, in a pass that walks about 30,000 items. Freya produces 5 mutations, then visits 57,050 layout nodes to recompute 14. GPUI beats most of them on this edit.

This is the distinction the argument depends on. All of those linear costs are in the engine respectively. Nothing in the application’s code requires them, so they can be fixed behind the same API without changing an application. zgui shows how far that goes: 0.69 ms for the label at 3,000 rows and about 0.26 ms per 1,000 rows, around 12 times flatter than GPUI. It is still not flat, and it is my framework and was tuned on this harness, so take these numbers with a grain of salt. In Iced and egui the linear cost is in the contract: the API says your code runs. No engine work can remove that, and app code has to change. GPUI probably sits somewhere in between, which is why gpui-fast can improve the situation to some extent.

At this point, I wan’t to share a more detailed benchmark matrix. Read the re-running columns down the first five rows and they barely move, because they do not depend on the edit. The signal columns move a lot, because the underlying implementations differ.

The bottom of that grid is also where the cost signals have becomes visible.

GPUI makes a full frame realitively cheap, and that makes it probably good enough for many use-cases. It is certainly enough for an editor whose expensive surface is handled by hand. For a large application it leaves a choice: keep the API people like and pay per view, or get precision by writing a signal graph out of entities. Elm and immediate mode have the same problem. What Nique Clifford to the Thunder means for the Spurs

📅 2026-11-09  |  Read Source →

The Thunder and the Kings completed an early-season trade that surprised most observers. Oklahoma City acquired second-year player Nique Clifford from Sacramento in exchange for two second-round picks, as first reported by ESPN's Shams Charania.

The trade is strange from the Kings' side, and we'll get to it. As far as the Spurs are concerned, however, the biggest impact comes from the Thunder once again getting cost-controlled, young talent for middling draft assets to bolster their depth in the present and the near future. Let's start there.

First things first: Clifford is not Jared McCain. All they have in common is that they were both second-year players whose previous teams gave up on them, and they were both traded to Oklahoma City for two second-rounders. The main difference between the two is that McCain was so impressive to start his first season in Philadelphia that he was the frontrunner for Rookie of the Year for a while, before getting hurt. Clifford, who entered the league at 23 years of age, had an acceptable but unimpressive first season for a horrible Kings team. The McCain trade was a bigger deal than this one at the time, and McCain's impact will likely be bigger than Clifford's in the future.

With that out of the way, it's still a good move for Oklahoma City, as they needed depth at the wing after losing Jalen Williams and likely Cason Wallace for the rest of the season. Clifford is 6'5 with a 6'8 wingspan, a jack-of-all-trades player who can fill in the gaps in lineups. He's someone who, in theory, can contribute in many different ways, which is always helpful for good teams that already have elite scorers and creators in place and can use guys who won't demand too many touches. There's a really good chance he thrives as a secondary or tertiary creator in Oklahoma City while providing solid defense. Considering what it took to get him, he's not a bad stopgap.

The real impact this trade could have, however, is on the future affordability of an increasingly expensive Thunder roster. Clifford is almost certainly not good enough to give OKC even half of the production of either of their starting wings who are out with injury, but he could be a solid depth piece going forward. He's in the second year of a very cheap rookie deal, so Sam Presti could get almost three years of production out of him on a cost-controlled contract, which means that when everyone returns, the Thunder could have both top talent and depth, which is becoming increasingly hard to do in the apron era.

By essentially re-drafting guys using second-round picks, OKC is building a pipeline of young talent to replace their own misses in talent evaluation and veterans who become too expensive.

That's bad news for every Western Conference team, including the Spurs.

Both analysts and people on social media are mocking the Kings for trading a first-rounder to OKC to select Clifford in the 2025 draft only to, just after a season and change, trade him to the Thunder for two seconds. It's a funny sequence of events from a poorly run franchise, so the jokes are understandable, but, in reality, it isn't as bad as it might seem at first glance.

First, the first-round pick the Kings traded to get Clifford was the Spurs' 2027 pick that they got in the De'Aaron Fox trade. The pick will likely be in the late 20s. Moving that asset for a pick of similar value (Clifford was selected 24th overall) was not necessarily a terrible idea by the Kings at the time, since they clearly liked Nique then. And cutting your losses if you think you made a mistake drafting someone is better than falling for the sunk-cost fallacy and holding on even after you've concluded the player just isn't good. Sacramento actually had to send out a second-round pick to shed former lottery pick Devin Carter Jr.'s salary, so they were probably trying to avoid doing the same with Clifford, who was out of the rotation.

But there might be an explanation for the trade that doesn't involve Sacramento thinking Clifford is a bust: the new lottery rules put the Kings in a bad position, and the move was a way to salvage something.

Starting next draft, the teams with the bottom three records will be in the relegation zone and will actually get worse odds of getting the top pick than a non-playoff team with a better record. The entire point of the change was to make sure coaches didn't just sit their veterans with fake injuries to tank as hard as they could while trotting out lineups featuring players who didn't belong in the NBA. It's entirely possible that the Kings felt like they needed to put guys on the floor who could lift them to at least the fourth-worst record, and thought Clifford was not one of them. Not yet, at least. At that point, trading him before he loses all value after being buried on the bench makes sense.

The Kings' reputation is so bad that explaining the move this way might seem too charitable, especially since even while playing their veterans, they are 1-8 and are a likely bottom-three team. Whether this specific move by this specific franchise is smart remains to be seen, but it wouldn't be shocking to see more mediocre-to-bad teams with young players that need developmental minutes that just aren't there moving on quickly while trying to get some value back.

If that's the case, contenders should be on the lookout for re-drafting opportunities, and Brian Wright should be ready to pounce if someone he likes becomes available.

NBA players regularly draw scrutiny for things they say to the press, but coaches tend to be reserved enough to avoid getting too much egg on their faces. With the Cavaliers down 3-0 to the New York Knicks, Atkinson was asked how he could give hope to his players, as no team in NBA history has ever overcome a 3-0 series deficit. "Analytically … we've won 2 out of 3," Atkinson said at the time. "We're two out of the three in the expected score. If you believe in process and all that, like, man, take that later. I don't throw that on them. I see it for myself, and if I have this feeling, I can go to our analytical table and be like, man, the expected score was like one point or two — us shooting way below expected, them shooting way over."

As Atkinson explained, analytics can estimate what a game's score should have been based on the shots both teams managed to produce and the expected field goal percentage of those shots. Essentially, if both teams shot exactly as the numbers suggest they would over a long sample, this is what the score would be. Atkinson did not specify which games he meant out of the three, but it was likely Game 1, which Cleveland lost in overtime, and Game 3, which New York won, 121-113. Prime Stats has an expected score metric that had Game 3 at a 113-113 tie, and while New York had an expected 10-point win in Game 1, that accounts for overtime. If the actual score had matched what Cleveland's analytics department projected in regulation, the game never would have gotten an extra period and the Cavaliers would have gone up 1-0.

Obviously, despite the expected scores, the Knicks led the series 3-0 at that point and had won those games by 40 total points. They went on to win Game 4 by 37 points, 130-93, though if it's any consolation, the Prime Stats expected score was a slightly less embarrassing 125-100. Both before the Game 4 sweep and afterward, Atkinson's quote was widely mocked. That includes jabs by multiple Knicks, as Josh Hart joked that "I guess we lost analytically" on his podcast with Jalen Brunson, and Karl-Anthony Towns, who said before the ESPYs that "analytically, we should win" the Best Team award. The word "analytically" has become shorthand for anyone attempting to justify an ugly defeat using numbers.

On Saturday, the Cavaliers faced the Knicks for the first time since that series. New York won again, 109-97, and yet again, the expected score was slightly more favorable to Cleveland, with Prime Stats posting an expected score of 112-103. Atkinson did not point to those numbers after Saturday's defeat. Instead, he attempted to explain the widely derided quote, arguing that the quote was taken out of context, which made the soundbite sound less flattering than his actual answer was.

"I would just say there was no coach more complimentary of the Knicks and honest about our performance and how they dominated us," Atkinson told reporters. "So you live and learn a little bit with those things. But like I said, 99% of my comments were how they dominated us. They were by far the better team. I answered the question, as it was taken, [which was] 'And you're down 3-0, what hope do you have of even giving to your guys?'

"We get a lot of information … and I wasn't lying in that sense, but in no sense was it like, 'Oh, man, we deserve to be winning.' Like zero — zero — thought of that."

Atkinson acknowledged that "no one wants to hear" about process when the outcome is a blown 22-point fourth-quarter lead and a 3-0 deficit, but he was trying to figure out how to rally his troops in an impossible situation. His phrasing has become a meme, but when you're down 3-0 in the playoffs, you'll grasp at any signs of positivity you can find. Atkinson had numbers suggesting the two teams were closer than the scoreboard suggested. Using those numbers to try to inspire his team made sense. Putting them out there in public risked exactly the sort of ridicule he ultimately got. The soundbite eclipsed the quote and the context, and the rest is history.
